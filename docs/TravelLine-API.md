# Подготовка TravelLine API — 10 ноября 2026

## Что установлено

В админке: Настройки → Настройки сайта → TravelLine.
Поля: включение API для закрытой проверки, тип авторизации OAuth/X-API-KEY, Client ID, Client secret, API key, propertyId, прежняя ссылка на бронирование.
Client secret и API key шифруются Laravel encrypted cast в БД и скрыты при сериализации. Пустое поле секрета в форме сохраняет прежнее значение. Секреты не передаются в HTML и клиентский JavaScript. Для восстановления зашифрованных значений необходим существующий APP_KEY: сохранить его в защищённом резервном копировании.

Закрытая форма: https://hotel-lermont.ru/_integrations/travelline
Доступ только активным администраторам с canManageContent; гостям предлагается вход /admin/login. Есть проверка Content API и собственная форма поиска без iframe: даты, взрослые, возраст каждого ребёнка, категории, тарифы, стоимость проживания и отдельно сборы при заселении. Предложений и цен-заглушек нет. Без настроенных доступов отображается понятное сообщение.

Серверный клиент: OAuth Client Credentials; зашифрованный кеш токена с запасом срока; блокировка параллельной авторизации; однократное обновление после 401 только для безопасных GET; ограничение частоты запросов; обработка 403/429/таймаутов без тела ответа и секретов в ошибках; фиксированный HTTPS-хост; проверка сертификатов включена. Справочники кешируются 5 минут, доступность и цены не кешируются.

Content API: GET /api/content/v1/properties/{propertyId}.
Search API: GET /api/search/v1/properties/{propertyId}/room-stays.
Reservation API: серверный метод verifyBooking для POST /api/reservation/v1/bookings/verify.
createBooking намеренно завершается отказом без отправки HTTP-запроса: публичное оформление, транзакционное состояние и оплата ещё не подключены. Конфигурация не позволяет случайно создать реальную бронь после ввода ключа.

## Как подключить полученные доступы

1. В TravelLine получить разрешения Content API, Search API и Reservation API (именно создание/verify, а не только Read Reservation). Подтвердить у TravelLine допустимость такого подключения для собственного сайта отеля и получить тестовый сценарий/доступы.
2. Заполнить Client ID, Client secret и propertyId в админке. OAuth нужен для Reservation API. X-API-KEY предусмотрен только для совместимых подключений Content/Search.
3. Сохранить настройки, включить API для закрытой проверки. Открыть ссылку под полем ID отеля.
4. Нажать «Проверить подключение», затем проверить поиск по датам с реальными категориями и тарифами, включая детей, ограничения и отсутствие мест.
5. Сверить ID всех шести категорий с существующими полями TravelLine в типах номеров. Поиск не перезаписывает описания, фотографии, удобства и SEO сайта.

## Что требуется до полного отказа от iframe

- Собственное оформление: выбор предложения с серверным хранением checksum/параметров, все гости и согласия, проверка verify перед подтверждением, явное согласие на alternativeBooking при изменении цены/условий.
- Создание: серверное хранение createBookingToken (одноразовый, срок по документации 24 часа), стабильный externalNumber, постоянный журнал попыток и блокировка дублей. При неизвестном результате/таймауте — сверка созданной брони, без слепого повторного создания.
- Эквайринг: Reservation API не предоставляет приём платежей. Нужны данные действующего провайдера и согласованный сценарий предоплаты/оплаты при заселении. Секреты эквайринга — серверные, карты на сервере сайта не хранить. Подтверждение оплаты только после проверенного webhook/статуса провайдера, не после перехода на success-URL.
- Подтверждения гостю: канал сам отправляет документы/уведомления, не полагаться на автоматическое письмо гостю от Reservation API.
- Отмена, расчёт штрафа перед отменой, изменения и возвраты, проверка статусов и сверка с TravelLine.
- Тесты с доступом: изменение цены между search/verify, последнее место, повторный клик, обрыв после создания, неопределённый результат платежа, отказ/возврат, отмена, письма и уведомления отелю.
- Отдельно решить замену guest-account и reviews-widget: текущие TL-виджеты личного кабинета и отзывов пока сохранены. Доступ Content/Search/Reservation не означает наличие API аутентификации гостей и программы лояльности.
- После успешной приёмки переключить публичную форму поиска, sticky-поиск, /booking и ссылки категорий, затем убрать TL loader на соответствующих страницах. Сейчас публичный сайт продолжает работать с прежним модулем.

## Проверки выполнены

На фиктивных HTTP-ответах, внутри откатываемой транзакции: шифрование и скрытие секретов; отказ при выключенном API; повторное использование токена; кеш справочников; передача взрослых и повторяющихся childAges; серверный propertyId; verify-адаптер; запрет реального create; рендер тарифов без iframe; защита гостя/менеджера; повторная авторизация GET после 401; режим X-API-KEY; обработка 429/Retry-After. Реальных броней, платежей и изменений в TravelLine не было. Проверен сохранённый tl-booking-form на публичной /booking.
